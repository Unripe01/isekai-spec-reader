# WRITING HARNESS

> 『異世界の仕様を読み解く者』を、即興性を残しながら長期連載するための実行手順。
> 目的地と世界ルールは固定するが、そこへ至る具体的な事件は執筆時に生み出す。

## 0. 基本原則

このハーネスの目的は、AIに過去全話を暗記させることではない。

**忘れても、管理ファイルと必要な本文から正史を復元できる状態を保つこと。**

- 世界の根幹設定を毎話変えない。
- 過去の伏線を忘れない。
- 同じ種類の設定を別名で増殖させない。
- 面白さだけを理由に新しい世界法則を追加しない。
- 過去のSYSTEM LOGと矛盾しない。
- キャラクターの性格を話の都合で変えない。
- 採用された即興は、その瞬間から正史として管理する。
- 想定規模は全30〜50話程度、中心値は35〜45話程度。ただし話数を固定せず、`STORY_ROUTE.md` のPhase到達条件と物語上の必要性を優先する。
- 100話以上続けることや、連載を続けること自体を目標にしない。
- 整合性、判断保留、意味更新は物語を壊さないための制約であり、それ自体を毎話の目的にしない。
- 記録は人物が誰かを助ける、追う、選ぶ、争うために使う。記録方法を改善することだけで一話を閉じない。
- 世界や他者から出来事が起こり、人物が欲望と危険を持って動く小説であることを、正史管理より優先して本文へ出す。

## 1. 新話執筆時の読み込み順

episode-Nを書く際、原則として次の順で読む。

1. `docs/series/WRITING_HARNESS.md`
2. `docs/series/STORY_BIBLE.md`
3. `docs/series/STORY_ROUTE.md`
4. `docs/series/CURRENT_STATE.md`
5. `docs/series/OPEN_THREADS.md`
6. `docs/series/CANON_LEDGER.md`
7. `docs/series/EPISODE_SUMMARIES.md`
8. `docs/series/NEXT_EPISODE_BRIEF.md`（存在する場合）
9. 直前二話の本文全文

episode-04なら、原則として `episode-02.md` と `episode-03.md` を全文確認する。

直前二話は、正史・人物・継続事項を確認するために読む。文体上の癖や改行頻度を無条件に模倣しない。文体については、作品本文よりも本ハーネスのルールを優先する。

### 古い本文を追加で読む条件

- 再登場人物の初出描写を正確に使う。
- 過去の台詞や物品を直接回収する。
- SYSTEM LOGの表記を再利用する。
- 地名、移動距離、日付、外見など、サマリでは不足する細部を参照する。
- CANON_LEDGERに不明点や証言差がある。

原則として、episode-01から全話を毎回全文読み直さない。

## 2. 執筆依頼の受け取り

新話を頼まれたら、本文を書く前に次を確定する。

- 対象episode番号。
- 直前話終了時の現在地。
- 現在のPhaseと出口条件。
- 今回進める既存伏線を一〜二本。
- 今回は進めない重要伏線。
- 話の冒頭で継続すべき直前の感情・行動・事件。
- ユーザーが指定した出来事、トーン、禁止事項。

具体的な事件が未指定でも、未来の全プロットを先に作らない。その話で必要な範囲だけ設計する。

## 3. 執筆前の内部チェック

本文へ書き出さず、内部で次を確認する。

### 正史

- 前話から時間・場所・同行者が自然につながるか。
- 人物の知識が `CURRENT_STATE.md` を超えていないか。
- 本文確定の地名、日付、外見、所持品、能力制約と矛盾しないか。
- 証言と確定事実を混同していないか。

### 伏線

- 今回どの既存伏線の意味を進めるか。
- 新設定を追加せず、既存の消失・破損・fallback・記録で説明できないか。
- 新しく出す謎を増やしすぎていないか。
- 既出ログと同じ意味の新用語を作っていないか。

### 連載進行と必要性

- この話は現在のPhaseを前へ進めているか。
- 既存伏線の意味を一つでも更新しているか。
- 本筋と関係のない新しい異常を追加していないか。
- 同じ種類の怪異を繰り返していないか。
- 「連載を続けるための話」になっていないか。
- このepisodeを削除しても本筋が変わらない場合、本当に必要か。

削除しても本筋が変わらない話でも、人物関係の自然な積み上げや、後の選択に必要な感情を成立させる場合は採用できる。その必要性を説明できない場合は、別話へ統合するか採用しない。

### 物語の駆動

整合しているだけの話、既存伏線を安全に一段更新するだけの話を採用しない。本文を書く前に、次を具体的な一文で答える。

- **欲望**：この話で中心人物は、今すぐ何を手に入れたい／守りたい／避けたいのか。
- **障害**：その望みを、誰または何が能動的に邪魔するのか。情報不足だけを障害にしない。
- **損失**：失敗した場合、誰が何を失うのか。命、信頼、居場所、時間、選択肢など、本文中で感じられるものにする。
- **選択**：中心人物は、観測や説明だけでなく、どの行動を自分で選ぶのか。
- **不可逆変化**：話の前と後で、状況、関係、目的地、責任のいずれが元へ戻らなくなるか。

五項目のうち一つでも「特になし」になる場合、その案は一話として弱い。別の事件と結合するか、出来事そのものを再設計する。

次の要約でほぼ説明できる案は、原則として棄却する。

> 矛盾を確認する → 記録を増やす → 書式や保管方法を改善する → 次の矛盾を持ち越す

記録所、会議、事情聴取、照合を主舞台にしてよい。ただし、その場で誰かの望みが阻まれ、判断の遅れや誤りによって具体的な損失が生じる場合に限る。

### 主人公の能動性

- ユウの事実確認、切り分け、判断保留は、誰かを救う、危険へ入る、追跡する、対立する、旅立つための手段として使う。
- ユウを、結論を保留して記録案を出すだけの監査担当者にしない。
- ユウ自身が何を望み、なぜ放っておけず、何を危険にさらすのかを本文へ出す。
- ユウが正解を出せなくても、自分の責任で行動を選ぶ場面を持たせる。

### 連続使用する題材の上限

- 同じ人物、同じ異常、同じ施設を続けて扱う場合、観測条件や帳票の種類を変えるだけでは継続理由にならない。
- 一つのテーマが読者へ十分伝わったら、未解決でも主筋から一度外し、背景で観測を続けてよい。
- 当事者を異常のテストデータとして扱わない。再登場させるなら、その人物自身の望み、恐れ、関係、決断を前へ進める。
- 静かな調査回の次に必ず戦闘を置く必要はないが、会議と照合が連続した場合は、移動、救助、追跡、襲撃、喪失、対立、期限など、人物を机から動かす出来事を優先して検討する。

### 事件密度と因果

- 「面白くする」ために、襲撃、火災、崩落、失踪、記録異常などを互いに独立した事件として一話へ積み重ねない。
- 危機を複数使う場合は、**原因 → 結果 → 時間制限**の一本の因果へまとめる。読者が別々のイベントとして処理しなくてよい形にする。
- 一話の中心は、原則として「一つの危機、一人または一組の助けたい相手、一つの重大な判断」で説明できる密度を目安にする。
- スケールを上げるより、中心人物が誰をなぜ助けたいのか、その判断に何を賭けるのかを深くする。

### 危機に置く人物

- 怪異や主題を示すためだけの名無しの被害者を置かない。救助、喪失、消失の対象には、短くても関係、癖、望み、誰かに覚えられている具体的な像を与える。
- 危機に置かれた人物を証拠、人数差、異常例だけとして扱わない。読者と主人公が「この人に間に合ってほしい」と思える場面を、危機の判断より前に置く。
- ミナやセドで生まれた感情を再利用する場合、同じ喪失を反復するだけにしない。今回は何を選べるのか、以前と違って何がまだ間に合うのかを描く。

### 戦闘・アクション

- 調査・会話・記録だけが続き、表側のダークファンタジー要素が長期間機能しなくなっていないか。ただし、この確認だけを理由に今回のepisodeへ無理に戦闘を追加しない。
- 今回戦闘を入れる場合、その戦闘が何を前へ進めるのか説明できるか。
- 戦闘を成立させるためだけに、新しい魔物、新能力、新しい世界異常を追加していないか。
- 既出の魔物、魔法、消失、破損、fallback、記録などの意味を、戦闘という状況から更新できないか。
- ユウの能力を攻撃スキルや即死能力として扱っていないか。
- ユウが異常箇所を見つけるまでに、観察、判断、試行、危険など必要な過程があるか。
- リゼやこの世界の戦闘職が、自分の能力と判断で戦う余地を持っているか。
- ユウが毎回最後の一手を担当する構造になっていないか。
- 戦闘の勝利だけで、その話の世界異常まで都合よく解決していないか。
- SYSTEM LOGや世界異常を取り除いても、戦闘場面そのものが剣と魔法のファンタジーとして読めるか。

### キャラクター

- ユウが突然万能になっていないか。
- ユウが正常な仕様まで自由に読んでいないか。
- 欠損したものを制約なく戻していないか。
- ユウのSEらしさをIT用語ではなく、事実確認・切り分け・記録・保留に出しているか。
- リゼが証拠を無視したり、説明係だけになったりしていないか。
- ユウとリゼの関係を、積み上げなしに恋愛へ進めていないか。

### 開示境界

- 読者に世界の真相を説明しすぎていないか。
- 作中人物が作者側設定を理由なく知っていないか。
- 現在Phaseで「まだ明かしてはいけないこと」に触れていないか。

## 4. 一話の設計単位

詳細な完全プロットではなく、執筆前に次の八点を持つ。

1. **継続**：前話の感情、行動、未解決から何を受け取るか。
2. **欲望**：中心人物が、この話の中で具体的に何を望むか。
3. **障害**：望みを阻む人物、事件、期限、危険は何か。
4. **損失**：失敗すると、誰が何を失うか。
5. **選択と行動**：中心人物が、自分の責任で何をするか。
6. **異常／主題の使用**：既存の異常や記録が、行動の中でなぜ必要になるか。
7. **不可逆変化**：状況、関係、目的、責任がどう戻れなくなるか。
8. **持ち越し**：次話を開きたくなる、現在の行動に由来する未解決。

「日常」「違和感」「意味更新」は演出と読後感の確認項目として残すが、一話の骨格にはしない。この三つだけでは調査報告や議事録でも条件を満たせるためである。

戦闘・追跡・逃走などのアクションは必須ではない。入れる場合は、欲望を阻み、損失を現実にし、人物の選択を迫る出来事として使う。物語上の意味を持たない独立したサービス戦闘として挿入しない。

毎話、世界規模を拡大する必要はない。静かな回でも、誰かが何かを望み、それを失う危険と、話の前へ戻れない変化を持たせる。

複数の危機を使う場合は、一つの発端から連鎖する因果として設計する。危機に置かれる人物は、異常を見せるための交換可能な対象にせず、中心人物が助けたいと思う具体的な理由を先に作る。

## 5. SSRルール

SSRとは、予定外だが作品を強くする即興展開を指す。即興そのものは歓迎する。

### 採用条件

次の五条件をすべて満たすこと。

1. 既存の出来事・伏線から自然に派生できる。
2. `STORY_BIBLE.md` と矛盾しない。
3. 将来回収できる問いとして記録できる。
4. 独立した新しい世界法則を安易に増やさない。
5. 全体を十話以上引き延ばす新規大設定にならない。

### 採用前の問い

- これは新設定か、それとも既知の事実の意味更新か。
- 既存の用語で説明できないか。
- 読者が「そういう世界だったのか」ではなく、「あの伏線はそういう意味だったのか」と感じられるか。
- 回収しなくても雰囲気で済む謎か、必ず答えが必要な謎か。
- 次の三話以内に説明する必要があるか、長期で保持できるか。
- 現在Phaseの目的を深めるか。Phaseを横へ広げるだけになっていないか。
- 必要な追加話数と回収先を説明できるか。

### 採用例

episode-03の「二人のセド」は、時間旅行という新設定を追加したものではない。episode-02の次の表示の意味を更新したSSRである。

```text
REGION LOAD FAILED
Attempting fallback...
Fallback source integrity: 62%
```

### 採用後

本文を書き終えたら、必要に応じて必ず次へ反映する。

- `CANON_LEDGER.md`
- `OPEN_THREADS.md`
- `EPISODE_SUMMARIES.md`
- `CURRENT_STATE.md`

**書きっぱなしは禁止。**

## 6. アンチAIガチャルール

新展開を考える際、最初に問う。

**「新しい設定を追加する」のではなく、「既に読者が知っている事実の意味を変えられないか」。**

### 避けるもの

- 毎話、新種の超常現象を追加する。
- 「今週の世界バグ」のように、異常を一話ずつ消化する構造を続ける。
- 似た現象に毎回別の英語ログ名を付ける。
- 回収予定のない固有名詞や秘密組織を増やす。
- 本筋と関係のない町や寄り道を、話数を増やすために追加する。
- 前話の危機より大きな危機を出し続ける。
- キャラクターが偶然、必要な知識や能力を持っている。
- 驚かせるためだけに過去の正史を無効化する。
- Phaseの出口条件を満たした後、同じ種類の事件で滞在を引き延ばす。
- 人物を観測対象として固定し、帳票、保管先、集計方法だけを替えて同じ問題を反復する。
- ユウが「未確定」と整理し、周囲が記録方法を改善しただけで解決感を作る。
- 主題を登場人物が会議で説明し、事件や選択より前面へ出す。

### 優先するもの

- 同じ異常を別の立場の人物がどう解釈するか。
- 既存の記録が別の証拠と食い違うこと。
- 正しかった事実の意味が後から変わること。
- 日常に一つだけ混ざる成立しない事実。
- ユウが「分からない」と記録し、後で条件が揃うこと。
- 世界や他者が人物へ問題を起こし、考える前に動かなければ誰かが失われる状況。
- 記録や観測が、救助、追跡、戦闘、交渉、決断のために必要になる展開。
- 解決できない異常の中でも、人物が何をするかは自分で選び、その選択が次の状況を作る展開。

## 7. 文体チェック

### スタッカート抑制

本作の通常文体は、短文を改行で連打するWeb小説的スタッカートを基調としない。

- 地の文は原則として、意味が連続する2〜5文を一段落にまとめる。
- 一つの思考、一つの因果、一つの状況説明は、原則として同じ段落で完結させる。
- 一文だけの地の文段落が3段落以上連続する構成は禁止する。
- 5語以下程度の極端に短い地の文を連続させない。
- 「短い一文＋空行＋短い一文」でテンポを作る方法を常用しない。
- 戦闘場面でも、動作を一動作ごとに改行しない。動作・判断・結果が一つの流れなら同じ段落にまとめる。
- 「違う。」「ただ。」「そして。」「普通だ。」「何もない。」などを単独段落として連続使用しない。
- 重要場面であっても、短文と改行を増やすこと自体を演出にしない。
- 強調のための一文独立は、一つの場面につき原則一回程度を目安とする。

悪い例：

> 黒牙狼が走った。
>
> 速い。
>
> ユウは下がる。
>
> 間に合わない。

良い例：

> 黒牙狼が一気に距離を詰めた。想像していたより速い。ユウは後ろへ下がったが、それだけでは足りず、次の瞬間には牙が目前まで迫っていた。

### 章末スタッカート防止

- 章末だからという理由で、地の文を短文化したり改行を増やしたりしない。章末も通常と同じ段落基準を適用する。
- 初稿後、最後の十〜十五段落だけを独立して再確認し、意味の連続する地の文を再結合する。
- 「それでも」「そして」「今は」「ただ」など、余韻を作るための短文を連続させない。
- 章末で強調する一文は一つに絞る。最後の台詞を引きとして使う場合は、その直前の地の文を滑らかにつなぎ、強調を台詞へ任せる。

### 執筆後のスタッカート確認

- 一文だけの地の文段落が連続していないか。
- 短文を結合しても意味や緊張感が失われない箇所は、段落としてまとめる。
- 原稿全体を見て、短段落の比率が高すぎないか。
- 戦闘場面の動作・判断・結果が、一動作ごとに不要な改行で分断されていないか。
- 強調のための一文独立が、一つの場面で繰り返されていないか。

### 怪異

- 怖さを形容詞で説明せず、成立しない事実を普通の文章で置く。
- 読者へ「ここが怖い／重要」と文章の形で教えすぎない。
- 日常、自然な会話、普通の説明を十分に置いてから、一箇所だけ異常を混ぜる。
- 簡単な言葉を、少しだけ嫌な位置に置く。

### 温度

- 本文はファンタジー小説の温度で書く。
- SYSTEM LOGとの落差を保つ。
- ユウとリゼの軽い会話を残し、全編を重苦しくしない。
- 通常場面まで名文・比喩・体言止めで飾らない。

## 8. SYSTEM LOGチェック

ログを出す前に、次を確認する。

- この話に本当に必要か。
- 既出ログの再登場または意味更新で足りないか。
- 本文だけでも怪異が成立しているか。
- ログが答えを説明しすぎていないか。
- 作中人物の誰に見えるのか明確か。
- 表記、大小文字、数値が `CANON_LEDGER.md` と一致するか。

ログは読者が忘れかけた頃に出る程度でよい。毎話の義務ではない。

## 9. 執筆後の正史更新

本文が確定したら、同じ作業内で次を行う。

### 9.1 CANON_LEDGER

- 新しく確定した事実。
- 新しい人物・地名・物品。
- 能力や世界ルールの意味更新。
- SYSTEM LOGの正確な表記。
- 後から無言で変えてはいけない事項。

### 9.2 OPEN_THREADS

- 新しい回収必須伏線を登録。
- 既存伏線が進んだら `OPEN`／`PARTIAL`／`CLOSED` を更新。
- SSRは関連伏線と接続し、独立法則として増殖させない。

### 9.3 EPISODE_SUMMARIES

三百〜六百字程度で、次を圧縮する。

- 何が起きたか。
- 何が確定したか。
- 何の意味が更新されたか。
- 人物関係に変化があったか。
- 次話へ何を持ち越したか。

### 9.4 CURRENT_STATE

- 現在話、場所、同行者。
- ユウ／リゼ／社会／読者の知識。
- 消失記録と重要所持品。
- 現在事件と直前話からの持ち越し。

過去の履歴を残さず、次話に必要な「今」へ置き換える。短く保つ。

### 9.5 STORY_ROUTE／STORY_BIBLE

- Phaseの出口条件を満たした場合だけ `STORY_ROUTE.md` を更新する。
- 作品全体を拘束する不変ルールになった場合だけ `STORY_BIBLE.md` を更新する。
- 新しい事件が起きただけで両ファイルを肥大化させない。

### 9.6 README

- 新話が確定したら、エピソード一覧、現在地の要約、ディレクトリ構成を更新する。
- 公開サイトへの反映を依頼された場合も、本文がドラフトであると明示されない限り、同じ作業で 9.1〜9.4 とREADME更新まで完了させる。

## 10. サイト公開用の同期

正史本文は `contents/episodes/episode-XX.md`。公開サイトはコピーを読み込む。

本文確定後、公開する場合だけ次を行う。

1. `contents/episodes/episode-XX.md` を `site/contents/episodes/episode-XX.md` へ同内容でコピーする。
2. 両ファイルが完全一致することを確認する。
3. `site/episodes/XX/index.html` を作成・更新する。
4. 前話／次話リンクとTOPのEPISODES／最新話導線を更新する。
5. ローカルサーバー経由で本文全文が読めることを確認する。

執筆依頼だけでサイト公開まで頼まれていない場合は、勝手に公開用ファイルを変更しない。

## 11. 完了条件

新話の作業は、次を満たして完了とする。

- 本文が直前話から自然につながる。
- STORY_BIBLEの不変ルールと能力制約を守る。
- 現在Phaseの開示境界を守る。
- 現在Phaseを前へ進め、そのepisodeが本筋または必要な人物変化へ役割を持つ。
- 新設定より既存伏線の意味更新を優先する。
- 中心人物の欲望、障害、失敗時の損失、選択、不可逆変化が本文中に存在する。
- 記録・照合・判断保留が目的化せず、人物の行動と危機のために機能している。
- 同じ人物や異常を、条件だけ変えたテストケースとして反復していない。
- 複数の危機が独立して盛られず、一つの因果へつながっている。
- 救助・喪失・消失の対象が、主題を示すためだけの交換可能な人物になっていない。
- 通常部分は滑らかに読め、一文一段落やスタッカート調が連続せず、短文が出たときだけ意味がある。
- 最後の十〜十五段落を再確認し、章末という理由だけで短文化した地の文や、余韻用の短文が連続していない。
- 採用したSSRと確定事項を管理ファイルへ反映する。
- 新話が確定している場合、READMEのエピソード一覧と現在地も反映する。公開依頼がある場合も省略しない。
- ユーザーが依頼していない改稿、公開、commit、pushを行わない。
